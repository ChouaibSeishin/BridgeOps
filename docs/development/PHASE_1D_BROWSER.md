# Phase 1D — browser onboarding, sessions and recovery

## 1D.1 browser session boundary

The frontend now uses the real authentication endpoints. Sign-in and refresh obtain signed CSRF under the origin-wide bridgeops-session Web Lock and omit Authorization. Access tokens remain in application memory; refresh credentials remain in HttpOnly cookies. All protected requests and anonymous mutations share the lock, including CSRF acquisition, so another tab cannot rotate cookies halfway through a cookie-sensitive sequence. No credentials are broadcast or persisted. BroadcastChannel sends only session-changed to clear other tabs after sign-in/sign-out; tabs then require explicit restoration/sign-in. The lock also works when BroadcastChannel is unavailable.

Current secure-context browsers with Web Locks are required (HTTPS or loopback development). Unsupported browsers fail closed with an explicit message. No unsafe localStorage lock fallback is used. Reload initializes once through CSRF, refresh and live /me. Expired credentials refresh before requests; a 401 permits one serialized refresh/retry. Network failures and 403/409/429 are not automatically retried. Backend live checks remain authoritative.

Sign-out and logout-all clear in-memory state even if the network fails; the UI distinguishes a locally cleared session from confirmed server revocation. No individual remote-session list is implied. Sign-in clears the password form after each attempt. Sensitive fetches use same-origin credentials, no-store and reject redirects. No service worker or persistent query cache is installed.

Focused frontend verification covers initialization, expired access, concurrent unauthorized calls, separate tab clients sharing a lock, failed refresh/network handling, both logout modes and safe form errors. Hosted CI must be inspected after publication; a build alone does not verify a real browser journey. Organization onboarding, recovery and end-to-end verification follow in the remaining increments.

## Operator prerequisites

Normal startup still provisions no account. Follow the [offline bootstrap guide](PHASE_1C_ONBOARDING.md), then open the same-origin frontend and sign in. Authentication must be enabled with signing material and the exact browser Origin; see [HTTP configuration](PHASE_1B_HTTP_AUTH.md). No persistent local account or real-recipient email is created by implementation verification. External SMTP remains disabled until configured.

## 1D.2 organization browser experience

The signed-in landing page lists real organizations and the API's pagination totals. The create form is shown from UserSummary.canCreateOrganizations, derived from current account grants on /me/login/refresh, never inferred from a tenant role. The backend still rechecks that grant at creation. Organization details expose current members, tenant-local roles, revision-checked changes/removal, invitation issuance/listing/revocation and safe errors. Client hints do not override server authorization. React Query state is memory-only, scoped by user and cleared when signed out.

New bounded reads: GET O/access returns {membershipId,permissions} for the caller's ACTIVE membership only; GET O/invitations?page=0&size=25 requires membership.invite and returns safe paginated {id,email,expiresAt,status,roleIds}, never tokens/hashes. Status is PENDING, EXPIRED, REVOKED or ACCEPTED. This listing is necessary so an invitation remains manageable after navigation/reload. Foreign/missing tenants remain uniformly 404. GET O/roles adds assignable, calculated from current permission subset and privileged-role rules. No migration or runtime privilege expansion is needed.

Existing recipients sign in, open Accept an invitation, and paste the emailed token. New recipients use Join with an invitation from sign-in, fill the invitation-only enrollment form and explicitly sign in afterward; enrollment creates no session. No proof is read from a URL. Unusable invitations retain a generic rejection because the anonymous API deliberately conceals exact failure reasons. SMTP-disabled/failure responses are shown as unavailable, never successful delivery.

Membership removal asks for confirmation and sends the current quoted revision in If-Match. Editing sends expectedRevision, status and tenant-local role IDs. A conflict requires reloading; last-active-Owner and delegation constraints remain enforced by the existing backend. There is no role-definition editor or fabricated workflow data.

## 1D.3 password management and recovery

Implemented POST /api/v1/auth/password/change {currentPassword,newPassword} requires live bearer identity, exact Origin and signed CSRF. Success 204 clears browser cookies, changes BCrypt credentials, invalidates outstanding reset proofs and revokes all families in one audited transaction. The browser clears its memory/query state, broadcasts a credential-free invalidation and requires sign-in again. Wrong current password/policy violations have safe generic errors; no old access credential remains valid after successful change.

POST /api/v1/auth/forgot {email} requires Origin/CSRF and returns the same 202 acknowledgement for eligible/unknown/disabled/unverified accounts and delivery failure/disabled SMTP. It acknowledges a request, never successful email delivery. Lookup/delivery run through a bounded volatile dispatcher (two workers, 32 queued requests), so SMTP/account lookup does not create an explicit synchronous public timing branch. Saturation/shutdown may discard work. Process failure loses pending jobs. There is no outbox, durable delivery, automatic retry or completion guarantee. Fixed operational warnings contain no account identifiers or provider details. Users can retry within quotas or contact the operator.

Only ACTIVE verified accounts receive recovery instructions. A fresh request invalidates previous pending proofs transactionally. Tokens are 256-bit random, stored only as SHA-256 hashes with a 15-minute absolute deadline. Email contains plain-text proof for manual body submission; no credential-bearing URLs. POST /api/v1/auth/reset {token,newPassword} requires Origin/CSRF, consumes the proof atomically, applies the centralized password policy and revokes all sessions/reset proofs with audit. Success is 204 with cleared browser cookies, never automatic login. Invalid/expired/reused/policy/eligibility failures share generic rejection.

V8 adds password_reset_tokens and only SELECT/INSERT/UPDATE(consumed_at) runtime rights. Runtime cannot extend deadlines or insert users. Account -> proof -> families lock order serializes recovery/change/session work. Event or mail failures roll back local state; an externally acknowledged mail followed by DB rollback contains an unusable proof. No external SMTP was used in tests.

The shared OutboundEmail port and TLS SMTP adapter live under shared.mail; identity never depends on organization repositories or delivery classes. Invitation wording remains in organizations. Existing INVITATION_SMTP_* Compose/environment settings and bridgeops.invitations.smtp.* properties are retained for compatibility and now configure the transport used by both purposes. Disabled remains the default. Recovery cannot deliver until these external credentials are configured; public generic acknowledgement deliberately does not reveal provider readiness. Invitation issuance retains explicit 503 on unavailable delivery. Both use mandatory authentication/TLS/hostname verification, bounded timeouts and no protocol logging/trust-all fallback.

Password policy is unchanged: at least 12 Unicode code points, maximum 72 UTF-8 bytes, BCrypt cost 12. Reset/change throttle windows add 20 attempts per peer and 10 per scope in 15 minutes, alongside existing global/peer limits and row cap. Reset scopes hash proof; change scopes use authenticated account ID; forgot scopes use normalized email. No credential appears in audit metadata, response DTOs, URLs or broadcast messages.

In the browser: Forgot your password opens the generic request form; I have a recovery token opens manual reset. Account & sessions includes current-password-confirmed change and both sign-out modes. No remote individual-session list is fabricated.

## 1D.4 required browser and release gate

Maven verify now requires built frontend assets and pinned Playwright Chromium. See README for clean-checkout order. The required BrowserJourneyIT uses a separate PostgreSQL container with restricted runtime credentials and separate operator fixtures, explicitly runs the existing bootstrap provisioner, starts the real HTTP application and serves the built React assets through a loopback test-only same-origin gateway. A random header protects test mailbox capture. Test source/gateway/capture are excluded from the production jar; no real provider is contacted and no account is created in local Compose. Missing browser/database prerequisites fail, not skip.

The browser journey verifies valid/invalid sign-in, concurrent tabs/reload and cookie/storage/cache behavior; create/list organization and members; issue/revoke and first-time invitation enrollment without auto-login; permission/foreign-tenant denial and revision-checked member change; logout; generic recovery with captured proof and invalidation of another active browser session; current-password change and logout-all. Backend integration tests additionally verify authenticated acceptance, strict proof expiry/replay/concurrency, delegation and last-Owner races. Playwright output logs only fixed step labels and safe rendered text on failure, with no tracing/video or credential-bearing URLs. Captures contain disposable synthetic API-backed data; password/proof inputs are masked.

Actual desktop/mobile/dark captures are in [screenshots](../screenshots/phase1d-organizations-desktop.png), [mobile](../screenshots/phase1d-organizations-mobile.png) and [dark](../screenshots/phase1d-organizations-dark.png).
