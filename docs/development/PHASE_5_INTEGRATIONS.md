## Accepted implementation contracts

- Keep the modular monolith, existing PostgreSQL worker and public application ports. Integrations owns configuration, secrets, catalog and persisted support/team/notification capabilities. Executions owns work/steps/attempts/results. Approvals owns immutable intent, decisions, signals and consumption receipts. Adapters never import another module's repositories/entities.
- Preserve graph schema/canonicalization v1 byte-for-byte. Schema v2 is separate: one manual or webhook trigger, one end, acyclic graph, at most 50 nodes/100 edges. Non-condition nodes have one exit; a condition has named true/false exits. Only the chosen path executes. Merges use the selected predecessor; they never await a skipped branch. No parallel fan-out, loop, schedule, script or general expression evaluator.
- V2 registered operations use typed bounded arguments, named earlier outputs and allowlisted paths. Batch limit 50; graph 128 KiB; trigger 256 KiB; response/intermediate/storage limits are explicit. Delay uses persisted due time; the unchanged 24-hour deadline includes every wait. Presentation coordinates stay outside executable canonical JSON.
- Support assignment intent contains exact ticket IDs, expected revisions, current assignment and target team IDs. Assignment, item receipt, result and audit are one local transaction. A changed item stops further writes and retains earlier committed outcomes; a revised plan needs a fresh execution/approval. Notification is persisted internal demo delivery with provenance, never external email/SMS.
- Sensitive business writes and configured REST writes always require a distinct eligible human through the central approval boundary, including graphs omitting an approval node. The existing bounded organization policy controls record approval/lifetime; business-write sensitivity is a fixed registered operation rule. Historical record policy/intent hashes remain unchanged. New intents bind actor type, exact arguments, source version/hash, logical operation and relevant connection revision/operation identity.
- Automation has an actual tenant-owned principal with scoped immutable-version/operation grants, live revocation and bounded admission. Human account/session authority is never inferred for an automated execution. Webhook endpoints pin an exact compatible webhook-triggered version and grant set.
- Webhook headers are X-BridgeOps-Timestamp (canonical Unix seconds), X-BridgeOps-Delivery-Id (bounded ASCII ID), X-BridgeOps-Signature (lowercase hex HMAC-SHA-256). Signing bytes are UTF-8 `v1\n{timestamp}\n{deliveryId}\n` followed by the exact body bytes. Verify signature before parsing, allow at most ±300 seconds skew, and deduplicate tenant-qualified endpoint/delivery receipts transactionally with execution submission. Same delivery/payload returns the original acknowledgement; changed payload conflicts. Revoked/rotated signing keys fail closed.
- Secret references are opaque UUIDs. AES-256-GCM uses a fresh 96-bit random nonce and 128-bit tag, with tenant/reference/purpose/key ID as authenticated associated data. PostgreSQL stores ciphertext/nonce/key ID only. Master keys live outside PostgreSQL in a protected mounted key directory. Missing/wrong keys have no plaintext fallback. New credentials create new envelopes/references; old key versions remain available until all references are explicitly rebound. Never return a saved credential through a later GET.
- Production REST is HTTPS on port 443, exact operator-approved DNS host, registered literal relative paths and typed request/response schemas. Workflow arguments cannot choose URLs/methods/headers. Reject special/private IPv4/IPv6, mixed DNS answers and rebinding. The connection's resolver must use only validated addresses; TLS verifies the original hostname/SNI. Disable redirects, proxy inheritance, transparent retries and credential logging. Bound DNS/connect/read/total time, bytes, rates and concurrency. Ambiguous writes require reconciliation; local keys do not prove remote exactly-once effects.
- Demo setup is opt-in, authorized, confirmed and idempotent. It adds SEEDED_EXAMPLE data without resetting existing content. Actual execution effects carry LIVE_EXECUTION provenance. Startup/migrations seed no tenant data.

## HTTP and browser contract

### Connection management and controlled transport

GET integration-definitions and GET integrations (bounded page/size), integrations/{id} and integrations/{id}/operations require integration.read. Summaries and operation field schemas exclude destinations, paths and secret references. GET integrations/{id}/configuration requires integration.manage and returns configuration plus credentialConfigured, never the saved credential. POST integrations creates a connection (201/Location); PUT integrations/{id} requires expectedRevision and returns the committed revision. Both require integration.manage. Name/description are public organization metadata; type is immutable. Disabled connections refuse new checks/dispatch. Versions and health histories are append-only and tenant-qualified.

Create body: {name,description,type,configuration,credential?}. Update: {expectedRevision,name,description,enabled,configuration,credential?,removeCredential?}. Missing credential retains the existing reference; a new credential creates a new encrypted reference. Empty/null credential values are not a way to retrieve or reuse a secret. Explicit removeCredential=true cannot accompany a new credential. Existing versions retain old references; GET never resolves them. Internal SUPPORT/TEAMS/NOTIFICATIONS configuration is exactly {}. REST configuration is exactly {baseDestination,operations,healthOperation}; healthOperation may be null, otherwise it must identify a registered read-only GET without path parameters.

Each REST operation is {id,method,path,pathParameters,requestFields,responseFields,classification,timeoutSeconds,maximumResponseBytes,remoteIdempotencyKey}. IDs and path segments are bounded; flat field types are STRING, INTEGER and BOOLEAN without coercion. GET is READ and has no body fields; POST/PUT/PATCH/DELETE are WRITE. At most 20 operations, 32 fields per request/response and eight path parameters are supported. Registered paths consist of literal alphanumeric/underscore/hyphen segments or declared {parameter} segments; substituted values are single alphanumeric/underscore/hyphen segments. Query strings, traversal, fragments, arbitrary headers, methods and absolute workflow URLs are rejected. Bearer credentials are 8–4096 RFC-style token characters; custom auth/header schemes and nested/array REST response schemas are not implemented. Provider output is projected to registered flat fields, bounded to 1 MiB, with duplicate/deep/malformed JSON, unexpected content type/encoding and credential reflection rejected.

POST integrations/{id}/test accepts {expectedRevision,effectsAcknowledged:true} for REST. Manager UI previews the saved destination, registered read operation and captured revision before confirmation. Missing/false acknowledgement rejects before admission/network contact. Internal checks require no remote acknowledgement. ConnectionChecks forbids a surrounding database transaction, authorizes/prepares a saved plan in a short transaction, admits the bounded call, rechecks the saved revision before contact, releases admission and records a sanitized check/audit in another short transaction. A result for an older revision is displayed as STALE, never as current availability. Connection edits are optimistic; conflicts retain configuration edits and require explicit reload. Credential input is cleared after submission and never stored in browser persistent storage.

HttpClient5 5.6.4 is managed by the retained Boot BOM. Its actual connection resolver validates every DNS answer and returns those exact addresses, with bounded DNS workers/queue and no second system lookup. Each call has its own one-connection manager; original-host TLS trust, hostname and SNI checks remain enabled. Redirects, proxy inheritance, cookies, compression, automatic retries and auth caching are disabled. DNS is bounded to two seconds and the operation deadline; connect/read/total duration and bytes are bounded. Network failures expose fixed codes/classifications without provider exception causes. Reads may be transient; an external write with an uncertain/lost response is AMBIGUOUS and must not be blindly retried. A supplied remote idempotency header is not an exactly-once guarantee. Workflow external dispatch/reconciliation is delivered with the graph-v2 runtime, not inferred from transport tests.

V13 adds ephemeral outbound admission slots. PostgreSQL serializes admission: max two active calls per connection, four per organization, eight globally, ten calls/minute/connection and 10,000 admission rows. Fifteen-second leases recover admission after a crash; bounded cleanup removes only expired admission metadata, never operation/webhook/approval receipts. Tests use a controllable clock for rate/lease recovery. 429 responses carry Retry-After:60. Actual health histories and operation receipts remain separate from these counters.

The production transport has no private-address or trust-all configuration switch. Disposable TLS tests use a package-private injected connection seam only from test sources, with a specific generated certificate/trust store and local ports. These fixtures do not establish external-provider connectivity. Approved host/operator semantics remain a trust boundary: labeling a provider GET as READ cannot prove the remote provider never performs a side effect.

### Encryption key setup and rotation

Fresh checkout: run scripts/setup-integration-secrets.ps1 after the existing setup scripts. Existing installation: run it only if secrets/integrations/local-v1.key does not exist; never rerun auth setup or bootstrap to add this key. The script uses CreateNew, 32 random bytes, restrictive Windows owner/SYSTEM ACLs or Unix 700-directory/600-file permissions and refuses overwrite. Compose mounts the key directory read-only. Docker Desktop mounts may expose synthetic POSIX modes; host ACL protection and the read-only mount are authoritative there. On writable POSIX filesystems the adapter rejects group/other permissions. Ciphertext is tenant/reference/purpose/key-ID bound, authenticated and never falls back to plaintext.

Optional configuration: INTEGRATION_SECRETS_ACTIVE_KEY_ID defaults local-v1; REST_ALLOWED_HOSTS is a comma-separated exact public DNS allowlist, empty by default. Existing .env is not replaced. Standalone properties are bridgeops.integrations.secrets.directory, secrets.active-key-id and rest.allowed-hosts. To rotate, explicitly create a different key ID with setup-integration-secrets.ps1 -KeyId local-v2, retain historical key files, switch the active ID externally and rebind credentials/signing references through authorized lifecycle operations. Merely changing the active ID does not re-encrypt old envelopes. Back up every referenced key with the database through a secure operator process; loss of a required key makes its ciphertext unavailable. There is no automatic rotation/retention job or managed-vault claim.

The key script was verified inside an ignored disposable copied-script directory: 32-byte creation, overwrite refusal and preservation of the old key while adding a version. Actual local signing/SMTP/environment material was not modified by that test. The optional .env.example settings contain no key or credential value.

Existing `/api/v1/organizations/{organizationId}` conventions, exact Origin/CSRF, live application authorization and foreign-resource concealment remain mandatory. Concrete DTOs are introduced with each adapter increment, including bounded pagination and safe 400/401/403/404/409/413/422/429/503 errors.

Planned route families: integration definitions and tenant connections/operations/checks; internal support tickets/teams/notifications and confirmed demo setup; automation principals/grants; webhook endpoint creation/rotation/revocation and one-time signing-secret reveal; signed `/api/v1/webhooks/{publicEndpointId}` callback; existing workflow publication and execution/approval monitoring extended for v2. Public callback authentication is HMAC, never ambient browser cookies or an anonymous run endpoint. Browser mutations remain protected.

GET automations (page/size) and automations/{id} require integration.read; POST automations/{id}/revoke accepts {expectedRevision} and returns the terminal REVOKED revision. V2 has exactly {schemaVersion:2,nodes,edges}. Every node has exactly {id,type,typeVersion:1,config,inputs}. Inputs is mandatory, including {} for nodes with no arguments. Triggers have {inputFields:{field:STRING|INTEGER|BOOLEAN}}; a single manualTrigger or webhookTrigger is allowed. Trigger input must contain exactly the declared flat fields, with no type coercion. Other configurations: syntheticAction {operation:record,message}; capabilityAction/configuredHttp {integrationId,revision,operation}; notification {integrationId,revision}; condition {operator,compare} or unary {operator}; approval {prompt}; delay {seconds:0..3600}; transform/end {}. Connection revisions start at zero. Internal operation IDs are support.list, support.get, teams.list, teams.get, teams.resolve, support.assignBatch and support.addNote; notification is its own registered node. Registration does not imply permission or a working runtime adapter.

Each input field is one of {literal:value}, {from:nodeId,path:registeredOutput}, or {parts:[literal-or-reference,...]} for at most 16 primitive interpolation parts and 2,000 resulting characters. Literals are bounded JSON with integral signed-64-bit numbers, booleans, bounded strings, objects/arrays (max 50 entries), depth eight and 512 values; no null, floating-point values or arbitrary expressions. Transform inputs name the selected/renamed output fields. Reference paths are single registered fields, except configuredHttp's response.field projection, which additionally requires the saved operation's response-field contract at binding/dispatch. No indices, wildcard, reflection, arbitrary object traversal or scripts. Errors include safe node IDs/field paths and fixed codes, never submitted values.

Edges are {source,target}, or {source,target,branch:true|false} where branch is a string and the source is condition. One trigger/one end, 50 nodes/100 edges, acyclic and fully reachable. Each condition has exactly two distinct outgoing targets with one true and one false label; every other nonterminal has one exit. Multiple incoming edges represent selected-predecessor merge, never parallel fan-out. Only the selected branch executes. Stable ID-based topological positions describe persistence, not execution order. Data sources must strictly dominate the destination: a source must occur on every route reaching that node. A branch-local output cannot feed a merge. Explicit approval must immediately protect a registered effect node and cannot supply arguments for that action from its own approval output.

Condition operators EQ/NE compare equal primitive types; GT/GTE/LT/LTE compare integers; EMPTY/NOT_EMPTY accept strings/arrays/objects. There is no coercion. The mapping engine copies source values, fails for missing/null output and bounds intermediate/assembled data to 1 MiB, 16,384 values and depth 16. Graph bytes remain 128 KiB, trigger bytes 256 KiB; stricter per-field limits also apply. Scheduled delay durability, skipped branch records, capability authorization and exact dynamic approval are runtime responsibilities, not claims made by pure graph validation.
